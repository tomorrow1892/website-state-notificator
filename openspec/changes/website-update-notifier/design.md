## コンテキスト

このリポジトリでは、GitHub Pages上の静的UIとGitHub Actionsで定期実行する監視フローを前提としたサイト更新通知システムを構築します。監視設定はリポジトリ内のJSONファイルで管理し、テーブルやデータベースは使いません。

この変更では、複数のURLを同時に監視し、LINE Messaging APIを使って変更を通知する仕組みを導入します。判定ルールは「出現」「消失」の両方に対応し、通常文字列と正規表現の両方を柔軟に扱います。

## 目標 / 非目標

**目標:**
- GitHub Pagesで静的ページをホスティングして設定を閲覧・編集できるようにすること。
- GitHub Actionsで定期的にページ取得と判定を行い、結果をLINEに通知すること。
- 複数の監視対象と複数のLINE受信者を扱えるようにすること。
- 各監視対象ごとに判定ルールとポーリング頻度を設定可能にすること。
- 設定と状態をリポジトリ内JSONで管理すること。

**非目標:**
- フル機能のサーバーサイドWebアプリやDBバックエンドを構築すること。
- ユーザー認証やマルチテナントをこの段階でサポートすること。
- HTMLの構造比較やDOM解析を行うこと。
- SMSやメールを送信すること（LINE通知に限定する）。

## 決定

### 実行環境
- 監視処理はGitHub Actionsのワークフローで定期実行します。
- 静的UIはGitHub Pagesでホスティングし、監視設定や結果の確認を行えるようにします。
- データはリポジトリ内のJSONファイルで保持し、GitHub Actionsと静的UIの両方から読み書きします。

### 監視設定
- 監視設定はJSON形式で管理し、各監視対象に次を含めます:
  - URL
  - 出現/消失のどちらを判定対象とするか
  - 通常文字列または正規表現のパターン
  - 複数のLINE通知先
  - 任意のポーリング頻度
- これにより、ユーザーは柔軟にルールを定義できます。

### GitHub Actionsでの周期実行
- 可能であれば、URLごとのポーリング頻度に応じて分けたワークフローを用意します。
- 難しい場合は、固定スケジュールで一括実行し、各監視対象の設定に従って判定だけ行います。
- たとえば、15分ごとのワークフローで全監視対象をチェックし、設定された頻度を内部で評価する方式が現実的です。

### 変化検出モデル
- 監視判定は、トリガーパターンの「出現」または「消失」で行います。
- パターンは通常文字列一致または正規表現のいずれかを選択できます。
- 前回の状態を保持し、変化があった場合にのみ通知を送信します。

### LINE通知
- 通知はLINE Messaging APIを使い、設定されたLINEユーザーまたはグループにメッセージを送信します。
- メッセージにはURL、判定ルール、前回の状態、現在の状態、および検出時刻を含めます。
- LINE APIのアクセストークンを安全に管理する必要があります。

### 状態永続化
- 前回の判定結果や取得時間はJSONファイルに保存します。
- GitHub Actions内での判定時にこのファイルを更新し、次回実行時に比較します。
- リポジトリのコミットベースで履歴を残す場合は手動マージやPR運用を検討します。

### エラー処理とリトライ
- 取得失敗やLINE送信失敗時は、他の監視対象の処理を継続します。
- 一時的な失敗はログに記録し、必要に応じて再試行を検討します。
- 変化検出の誤検知を防ぐため、取得エラーでは通知を送信しません。

## リスク / トレードオフ

- [Risk] GitHub ActionsのスケジュールはURLごとの細かい頻度管理に向かない。
  → 対策: 固定スケジュールで一括実行し、監視対象設定に応じて内部判定する方式を採用する。
- [Risk] LINE Messaging APIのアクセストークン管理と送信制限が課題になる。
  → 対策: アクセストークンはGitHub Secretsで管理し、失敗時のリトライを制限する。
- [Risk] 正規表現を使うとユーザー設定が複雑になる。
  → 対策: UIやドキュメントで使い方を明確にし、通常文字列モードを推奨する。
- [Risk] JSONファイルで状態管理すると複数人編集の競合が発生する。
  → 対策: ファイル更新はGitHub Actions内でシンプルに行い、競合時には手動解決を促す。
